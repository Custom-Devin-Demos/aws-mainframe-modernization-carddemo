# COBTUPDT parity fixtures

Every `expected/` file was generated by `tools/cobol/run_scenario.sh`, i.e. by the **original COBTUPDT COBOL**
compiled with GnuCOBOL 3.1.2. Its five `EXEC SQL` blocks are replaced by calls to a small COBOL Db2 stand-in
(`tools/cobol/TTDBSHIM.cbl`) over BDB indexed files, because GnuCOBOL cannot run `EXEC SQL`. The SQLCODE
semantics of that stand-in (`0`, `+100`, `-803`, `-532`) are an independent model of Db2 written from
`ddl/TRNTYPE.ddl` and `ddl/TRNTYCAT.ddl`, not from the Java job. None of these files came from running the Java
job. See `tools/cobol/README.md`.

Per scenario, `expected/` holds:

| File | Derived from |
|---|---|
| `transaction_type.csv` | TRANSACTION_TYPE indexed file after the run (`TTUNLD`), sorted by `TR_TYPE` in EBCDIC (CCSID 37) order, strings right-trimmed. Compared with the `transaction_type` Parquet. |
| `maintenance_log.csv` | One row per INPFILE record, rebuilt by `to_canonical.py` from the COBOL DISPLAY lines (`PROCESSING ...`, the action line, the result/WS-RETURN-MSG line) and the shim's SQLCODE trace. Compared with the `maintenance_log` CSV. |
| `sysout.txt` | The program's DISPLAY output, each line right-trimmed. Compared line for line with the job's SYSOUT. |
| `run.properties` | `return_code` = the COBOL program's exit status (RETURN-CODE); counters counted from `maintenance_log.csv`. |

## Inputs

No sample `INPFILE` exists, so each scenario has a hand-written `input/INPFILE.txt` (53-byte records:
type, tr_type, description; trailing blanks stripped as in the ASCII unloads).

| Scenario | TRANTYPE / TRANCATG | INPFILE covers |
|---|---|---|
| `sample-data` | the real `app/data/ASCII/trantype.txt` and `trancatg.txt` (no copies in `input/`) | comment, add OK, duplicate add (-803), update OK, update not found (+100), FK-restricted delete of `01` (-532), delete OK, delete not found (+100), invalid type `X`, message carry-over, RC 4 |
| `all-success-rc0` | 3 types, categories for `01` and `03` | add, update of the row just added, delete of an unreferenced type, re-add of a deleted key, update, delete, comment `*` alone; RC stays 0 |
| `message-carry-over` | same | WS-RETURN-MSG is never cleared: shorter messages overlay longer ones (`ERROR: TYPE NOT VALIDSACTION_TYPE table. SQLCODE: -532`); processing continues after every 9999-ABEND; a later success does not reset RC 4 |
| `invalid-and-blank-records` | same | lower-case `a`/`d`, digit and blank types are invalid; an empty line is an all-spaces record; `U02` with blank description sets it to blanks; leading spaces kept; 50-character description; blanks after column 53 ignored; comment with leading spaces |
| `ebcdic-collation` | 2 types, 1 category | non-numeric keys (` 1`, `ab`, `AB`, `A1`, `Z9`, `0A`, `1 `) to pin the Db2 EBCDIC `ORDER BY TR_TYPE` order (space < lower case < upper case < digits) |
| `empty-input` | same as `all-success-rc0` | empty INPFILE: only `OPEN FILE OK`, unchanged snapshot, RC 0 |

The small `input/TRANTYPE.txt` / `TRANCATG.txt` files use the sample-file layouts (CVTRA03Y 60 bytes,
CVTRA04Y 60 bytes) with descriptions copied from the sample data.

## Regenerating

```bash
app/java/carddemo-batch/jobs/cobtupdt/tools/cobol/run_scenario.sh   # needs gnucobol3
```

Review the diff of `expected/` by hand. A change there is a change in COBOL-derived behaviour.
